## What is Expresso Portal?

It is the team's operating workspace for clients, sales, service scope, delivery, creative work, invoices, HR, procurement, communication and website publishing. Clients and vendors use the same application with restricted access. It is not a complete accounting, payroll, inventory, social publishing or clinical CAS application.

The repository contains one React application with two surfaces: public marketing pages and `/portal/*`. One Express API serves both. The portal is separated by its layout, styles, login and server permissions, not by a second database or a separate deployment boundary. Public inquiries can either leave the platform through EmailJS or enter CRM through the plan-builder endpoint; those are different journeys.

The current source inventory also includes [Operating Model Phase 1](OPERATING-MODEL-PHASE-1.md). Its internal delivery implementation leaves the closed Blueprint conclusions and external deployment acceptance unchanged.

## Where is data stored?

MongoDB stores accounts, permissions, client records, operational work and editable content through Mongoose. The connection is configured by `MONGO_URI`; this audit did not inspect its value or identify a live Atlas/local deployment. Uploaded bytes live separately: public assets in S3 or development `uploads`, confidential files/CVs in private storage or development `private-uploads`. MongoDB stores references, keys and URLs, not the underlying object backup.

Deleting MongoDB does not delete S3/local files. Conversely, preserving files without their ownership/reference records does not preserve a usable portal. Some older fields contain arbitrary/public URLs rather than secure managed file references.

## How are users controlled?

The API verifies a Bearer JWT, loads the current active User, resolves Role permissions plus user grants minus revokes, strips prohibited external capabilities, and applies endpoint/controller ownership rules. The browser's stored user/permissions only control presentation. Built-in role defaults exist in code; custom Role records and user/company links need preservation. Public signup is not unrestricted account creation: invite acceptance and approved vendor applications are the implemented onboarding paths. Google login requires an existing active account.

## What is CMS-controlled, and what is core?

CMS controls slides, website image/settings overrides, public service records, Solution marketing records/groups, case studies (the `Portfolio` model, `/case-studies`), Portfolio work items (`WorkItem`, `/portfolio`) and careers. It also uses shared Media metadata. Much homepage/About/pricing/product copy remains in code; HR staff do not automatically populate the public team section.

Core application definitions include route contracts, permission keys/default roles, workflow constants, technology group fallbacks, brand assets and the core Digital Product registry. **CAS remains discoverable without a CMS record and through API outages.** Its existing metadata is reused by `coreDigitalProducts.js`; published CMS metadata can enrich it. The dedicated CAS page is not duplicated in that registry, and its clinical operating system/database is not present in this repository.

Internal ServiceTemplate records are business configuration, not public DigitalService CMS records. Customer, CRMAccount, Project and Portfolio likewise represent different concepts; do not merge them simply because their names look similar.

## What would break if MongoDB were emptied?

- Every portal login, Google login, invite acceptance and existing client/vendor relationship would stop working until required identity records were restored/recreated. A connected, empty MongoDB can still let the HTTP server start.
- Custom roles, team/category IDs, approved service templates, KPI definitions and website settings/content would disappear. Built-in role *code* survives; it does not recreate user accounts or custom configuration.
- Public CMS service/Technology detail pages would have no records; galleries, vacancies and reels would be empty. Static sitemap/detail links could then lead to missing content.
- Vendor category selection/matching would be unusable without the category tree. The audit-baseline vendor RFQ authorization mismatch was corrected in R2; restoring approved categories/content is still required for a usable vendor portal.
- CAS/core product discovery and its dedicated static page would survive. Core marketing/brand defaults can still render; that is not a complete restoration of approved website content.
- Storage objects and external configuration would remain, but many ownership/reference records would be gone. SiteSettings reads no longer recreate a singleton (R4-B): they return model defaults until an admin saves, and cannot recover approved settings.

## What is safe to reset?

Nothing has been approved for deletion. The database map classifies schema purposes: **3 SYSTEM, 6 CONFIGURATION, 8 CMS, 29 BUSINESS, 1 LOG/AUDIT; 0 confirmed TEST/LEGACY collections**. BUSINESS means potentially resettable after an approved retention/reference plan, not disposable. Finance, HR, applications, conversations, published Jobs and shared assets need explicit decisions. Preserve/recreate stable IDs and configuration deliberately; never identify whole collections as test-only from the appearance of a few records.

## Main architectural risks at the audit baseline (historical)

1. **Authorization contracts differ by layer.** Static UI permission catalogs/defaults, route gates and controller role rules disagree. Project create, update and delete, and ticket delete, skip the company check, which matters if an external role is granted those keys. Invite tokens are written to production request logs.
2. **Public publication is not consistently server-enforced.** Public Portfolio/Production reads can return drafts; web-content's inactive/detail reads are not protected management-only reads.
3. **Vendor registration is ahead of vendor access.** Vendor-specific RFQ controllers and UI exist, but internal-only read gates and the frontend denylist block the journey.
4. **Multi-record workflows are not transactional.** Vendor approval and CRM conversion can leave partial state after a mid-flow failure. Invoice numbering can fail under simultaneous creation; RFQ numbering can duplicate. Project DELETE is a permanent delete that orphans linked records.
5. **Reset and storage lifecycles are not one controlled process.** Existing seeds mix reference content, samples and updates; there is no approved backup/reset/system-seed/demo-seed pipeline. Account deletion has source-confirmed identity/import bugs.

**Update — Stage R3 (CLOSED; historical summary):** invoice and RFQ numbers come from an atomic per-year counter (new `counters` collection; RFQ unique index still waits for a read-only duplicate check), project DELETE archives instead of deleting, and `seedUser.js` is insert-only (P2-3, P2-4, the `seedUser.js` part of P2-7); see the remediation plan. **Update — Stage R2:** the access model and vendor journey items are implemented and covered by automated tests (P1-1, P1-3, P1-4, P1-5, P2-1, P2-5, P3-4 and the external-role policy of P0-2); see the remediation plan. **Update — Stage R1:** P0-1 to P0-4 (items 1, 2 and the log/admin issues above) have been fixed and covered by automated tests; see the [remediation plan's implementation status](REMEDIATION-PLAN.md#implementation-status). The findings in this audit describe the code at `58b8f86c`.

## Original cleanup findings (historical)

The import graph identifies **79 JavaScript/JSX files not reachable from the current React entry point**. These include older dropdowns/public hard-coded service pages, production experiments and wrappers duplicated by inline calls. Some reusable components should be kept or consolidated rather than deleted. Older auth helpers, three unused backend utilities and four empty backend files are also candidates (24 zero-byte source files in total). The mounted Production API/model must not be removed solely because its old public pages are unreachable. See the classified candidate list; no files were removed.

## Original proposed cleanup sequence (historical)

1. Approve the security/authorization and publication-boundary findings; add targeted tenant/role contract tests before changing access.
2. Choose authoritative role/permission, job workflow and upload contracts; align UI and API without weakening server checks.
3. Define approved business configuration versus demo data; reconcile public CMS content and shared storage references.
4. Build and test a restore-verified backup and selective reset procedure in an isolated disposable environment.
5. Consolidate overlapping workflows/APIs and remove only reviewed unreachable code/dependencies.
6. Re-run role-specific journeys and publication checks. Begin later visual work only as a separate authorized stage.

## Audit method and validation

Source review covered both routers, all model files, mounted Express route declarations, controllers/services, permission resolution, upload/email/Google integrations, seed scripts and feature imports. Static inventories are reproducible. No `.env` file was read, no database was queried, no application login/business action was executed, and no external service or storage configuration was changed. Default collection names and code counts are distinguished from live deployment facts.

Run `node docs/architecture/generate-inventory.cjs --check` and `node docs/architecture/validate.cjs` from the repository root. The validator re-checks every count, classification total, endpoint row and link in this folder against the source inventory, confirms the blueprint makes no network requests, and scans the documents for anything that looks like a credential. The offline HTML is independently rendered at desktop/mobile sizes and requires no remote fonts, scripts, images or API calls. Existing application test results from previous implementation work are not presented as tests run by this documentation audit.
